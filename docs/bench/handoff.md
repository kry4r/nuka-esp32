- 镜像：`firmware/build/nuka-esp32.bin`，1,826,752 字节，版本仍为 `0.1.0`；SHA-256：`8e15ae52d2a23333ae40f1d949bcb62cb3c311b517ea1805459d0d861fefaf7e`。对应 `firmware/build/nuka-esp32.elf`。同版本号不足以区分镜像，必须核对哈希和 ELF。
- 本轮先核对原厂 `backups/factory-16m.bin`：16,777,216 字节，SHA-256 `6eb72d4907d0ad647f8a7423ad01a95eac227878249f59c33d50187f865d1ed8`，备份不进 git。
- 维护者手动进入下载模式；自动识别端口并独占打开成功。只读核对设备分区表与本地构建一致，两份 OTA 记录为 `(sequence=1,state=VALID)`、`(sequence=2,state=VALID)`，选中已确认的 `ota_1`。
- 仅写 `ota_1` 应用地址 `0x430000`，esptool 报告 `Hash of data verified`，随后再次比较目标区 MD5 与镜像一致。没有写 bootloader、分区表、OTA 选择、NVS、Vault 或资源。
- 使用同一 loader / 串口连接完成读取和写入，避免之前关闭 ROM CDC 后重新枚举造成中断。watchdog reset 后 USB 断开，应用 CDC 恢复。
- 本轮第一次封装调用误让 esptool 重载已运行的 stub，在任何写入前失败；改为复用 loader 调用 `cmds.write_flash` 后完成写入及验证。
