## 1. 总览

### 1.1 轨道
| 轨道 | 范围 | 主要产物 | 执行者 |
|---|---|---|---|
| **C 契约** | 协议 schema 与样例、设计 token、仓库骨架、CI 骨架 | `protocol/`、`design/theme.json`、`AGENTS.md`、CI | 契约 agent（最先执行，任务量小） |
| **FW 固件功能** | 整套设备系统：系统核心（启动顺序、任务模型、事件总线、vm_store、NVS 存储、日志、看门狗）、板级驱动、系统服务（电源、电池、网络、Hub 客户端、USB、Vault、OTA）、UI 框架、各 App 的**逻辑与功能版视图**、SDL 模拟器、网页刷机页 | `firmware/`、`site/` | 固件 agent |
| **BE Hub 后端逻辑** | Hub 的全部服务端逻辑、CLI、插件、REST/WS、打包，以及**简单的 Web 配置管理页**（美观、能看即可，见 SPEC §7.13） | `hub/` | 后端 agent |
| **INT 系统联调** | FW 和 BE 都完成后，用真实设备和真实 Hub 跑通整个系统（INT-01）；只记录问题和复现步骤，交给 FW / BE 修复后复测 | `docs/bench/e2e-*.md` | 集成 agent |
| **FE 前端优化（最后的大项）** | **只针对 ESP32 屏幕上的 LVGL UI**：交互与功能完整度走查、视觉精修、动效、渲染性能、**低功耗打磨**、桌宠美术、图标、开机画面、截图 | `firmware/**/*_view.c`、`firmware/components/ui/` 中的视觉部分、`assets_src/`、`design/`；M7 阶段还包括功耗参数（§2.1） | 前端 agent |

### 1.2 依赖与并行关系
```
C-01..C-03 ──┬──> FW-00 … FW-29（整套设备系统，M1–M6）────────┐
             │                                                ├──> INT-01 系统联调（M6.5）──> FE-D1 … FE-D8（ESP32 LVGL UI 优化 + 低功耗，M7）──> INT-02 … INT-04（M8）
             ├──> HUB-01 … HUB-31（Hub 后端 + 简单 Web 管理页，M3–M5）┘
             └──> 各轨道负责编写自己功能的安装引导（DOC-*）
```
- **先把系统做对，再把 UI 做漂亮**：M6.5 之前的所有工作（C、FW、BE、INT-01）只追求功能正确、系统稳定；视觉、动效和功耗打磨统一放到 M7。
- **FW 和 BE 完全并行**，双方只依赖 C 轨道冻结的契约。联调前，各自用模拟器代替对方：
  - FW 用 `protocol/examples` 中的样例帧 + `nuka hub --demo`；
  - BE 用 `nuka sim-device`。
- **INT-01** 要等 M5 和 M6 都完成：用真实设备、真实 Hub 和本地假上游（假 CPA / CPAMP、假探针）跑附录 C 的场景。
- **FE** 要等系统联调通过（M6.5），这样打磨的是一个已经跑通的系统。FE 开发时只需要 `nuka hub --demo` 提供数据。
- Web 管理页（HUB-31）由 BE 顺带完成，要求美观、能看即可，不单独安排轨道。

## 2. 协作规则

### 2.1 目录归属（谁可以改哪里）
| 路径 | 归属 | 其他轨道 |
|---|---|---|
| `protocol/`、`docs/PROTOCOL.md`、`docs/CONFIG.md`、`design/theme.json` | C | 只能走 §2.3 的契约变更流程来修改 |
| `firmware/`（下面两行除外） | FW | FE 可以提 issue，不直接修改 |
| `firmware/components/apps/*/*_view.c`、`firmware/components/ui/{theme.c,anim.c,widgets/*}`、`firmware/assets_src/` | 在 M6.5 之前归 FW（写功能版，并修复联调中发现的问题）；**M6.5 之后转交给 FE** | 转交之后，FW 只修 bug，并且要通知 FE |
| `firmware/components/apps/app.h`、`*_app.c`、`ui/nav.c`、`ui/keynav.c` | FW | FE 需要新的数据或动作时，向 FW 提需求 |
| 功耗相关参数：`svc/power.c` 中的时序常量、`sdkconfig.defaults` 中的 PM 和 Wi-Fi 省电项、LVGL 刷新周期、各 `lv_timer` 的周期 | M6 之前归 FW；**M7 阶段由 FE 调优** | 只改参数和调度策略，不改状态机结构；改动要在 PR 中通知 FW |
| `hub/`（包括 `hub/src/nuka_hub/web/` 中的简单管理页） | BE | — |
| `site/`（网页刷机页，GitHub Pages） | FW | — |
| `docs/bench/e2e-*.md`（系统联调报告） | INT | 各轨道只更新自己负责问题的状态 |
| `docs/guides/<nn>-*` | 由实现该功能的轨道负责（见 §7） | — |
| `docs/SPEC.md`、`docs/PLAN.md`、`AGENTS.md` | 维护者 | agent 可以提出修改建议，不直接修改 |
| `local/` | 维护者个人使用，git 已忽略 | **任何 agent 都不得读取其中的内容写进仓库** |

### 2.2 交付规范
- **分支**：`<track>/<card-id>-<slug>`，例如 `be/hub-16-ai-passive`。一张任务卡对应一个 PR；比较大的卡可以拆成几个 PR。
- **PR 描述**中必须包含：
  - 对应的任务卡 ID；
  - 验收项逐条勾选；
  - 手工验证的方法与结果；
  - 是否改动了契约（默认"否"）；
  - 涉及 UI 的 PR 附上截图。
- **完成定义（DoD）**：
  1. 任务卡的验收项全部满足；
  2. CI 通过；
  3. 零硬编码检查通过；
  4. 新增的集成附带了对应的安装引导（或者在引导中补齐了相应章节）；
  5. 没有违反 AGENTS.md。

### 2.3 契约变更流程
1. 在 issue 或 PR 中说明需要修改的原因和具体改法。
2. 先修改 `docs/PROTOCOL.md` 或 `docs/CONFIG.md`，以及对应的 schema 和样例，作为一个单独的 PR。
3. 维护者批准后合入；有不兼容的改动时，同时提升 `proto`。
4. 各轨道再分别修改自己的实现。

**禁止**在实现 PR 中顺手修改契约。

## 3. 任务卡格式
每张卡都包含以下字段：**依赖**、**参考**（SPEC / PROTOCOL / CONFIG 中的章节）、**产出**（文件或命令）、**要点**、**验收**，以及**规模**（S ≈ 半天，M ≈ 1–2 天，L ≈ 3–5 天，按 agent 的工作量估算）。

验收以"可以观察到的行为"为准。按 AGENTS.md 的要求，**不要**为了验收额外编写测试；只有标注了 T1–T8 的卡需要写自动化测试（对应 SPEC §10.1）。

## 4. 轨道 C：契约

### C-01 协议 schema、样例与校验脚本（M）
- **依赖**：无
- **参考**：PROTOCOL 全文
- **产出**：
  - `protocol/schemas/*.json`
  - `protocol/examples/**`：每种消息至少 1 个样例，每个 VM 主题至少要有"满字段"和"最少字段"两个样例
  - `protocol/wmo_icon_map.json`
  - `scripts/check_protocol.py`（T6 的一部分）
  - `protocol/README.md`
- **要点**：
  - schema 使用 JSON Schema 2020-12，以 `t` 字段作为 `oneOf` 的判别字段；
  - 字段的约束（上限、枚举、字符串长度）必须与 PROTOCOL 完全一致；
  - 样例中只使用占位符数据。
- **验收**：
  - `python scripts/check_protocol.py` 校验全部样例都通过；
  - 故意改坏一个样例时，脚本能报错，并指出出错的字段。

### C-02 设计 token 与生成器（S）
- **依赖**：无
- **参考**：SPEC §6.6.1–6.6.2
- **产出**：
  - `design/theme.json`
  - `firmware/tools/gen_theme.py`，生成 `firmware/components/ui/theme_tokens.h` 和 `hub/src/nuka_hub/web/theme.css`
- **要点**：
  - 生成 CSS 变量（供 Web 管理页使用）；
  - 校验对比度，不达标时退出码非 0。
- **验收**：
  - 两份产物都能生成；
  - 把 `text_dim` 改成一个暗色值时，构建失败。

### C-03 仓库骨架、CI 与零硬编码检查（M）
- **依赖**：无
- **参考**：SPEC §3；本文 §2；AGENTS.md
- **产出**：
  - 顶层目录：`firmware/`、`hub/`、`protocol/`、`design/`、`i18n/`、`docs/guides/`、`scripts/`、`site/`
  - `.gitignore`（包括 `local/`、`build/`、`sdkconfig`（只提交 `sdkconfig.defaults`）、`.venv/`、`*.nukavault`、`secrets.toml`）
  - `.github/workflows/`：
    - `firmware.yml`：在 ESP-IDF 5.5 容器中编译，另外用 6.0 编译一遍，允许失败；
    - `hub.yml`：在三个平台上安装，然后运行 T1–T6；
    - `protocol.yml`
  - `.github/pull_request_template.md`
  - `scripts/check_no_personal.py`
  - `LICENSE`：AGPL-3.0 全文；`THIRD_PARTY.md`：依赖与许可证清单（SPEC §3 原则 7）
  - `scripts/check_license.py`：检查每个源文件头部是否有 `SPDX-License-Identifier: AGPL-3.0-or-later`，并在 CI 中运行
- **零硬编码检查的规则**：
  - 扫描所有提交到仓库的文本文件。
  - 公网 IPv4 地址只允许出现 RFC 5737 文档地址（`192.0.2.0/24`、`198.51.100.0/24`、`203.0.113.0/24`）；私网地址只允许出现在 `config` 默认值与示例中。
  - 域名只允许 `example.com`、`example.lan`，以及一个白名单（上游项目和依赖的官网）。
  - 如果存在 `local/blocklist.txt`，就把其中的关键词也加进检查（这个文件由维护者在本地维护，CI 上不存在）。
- **验收**：
  - 三个 workflow 能在空骨架上跑通；
  - 在任意文件中写入 `203.0.113.5` 时检查通过；写入任意一个公网真实 IP 时检查失败。

## 5. 轨道 FW：固件功能
> 通用要求：
> - 使用 ESP-IDF 5.5.x 和 C11；
> - 只有 `lvgl` 任务可以调用 LVGL；
> - **只在网络帧、CDC 输入和 NVS 读出这些边界处做校验**；初始化失败时直接 `ESP_ERROR_CHECK`；
> - 只写 SPEC §10.1 中的 T7、T8 两项测试。

### FW-00 工程骨架与系统核心（M）
- **依赖**：C-03
- **参考**：SPEC §1.1 的系统分层、§6.1、§6.2、§6.2.1、§6.3.2、§6.4.1、§6.15、§6.17
- **产出**：
  - `firmware/` 工程、`partitions.csv`、`sdkconfig.defaults`、锁定版本的 `idf_component.yml`；
  - `main/app_main.c`：按 SPEC §6.2.1 的启动顺序搭好框架，还没实现的步骤先留空函数；
  - `svc/nuka_events.h` 与事件循环 `nuka_bus`；
  - `svc/vm_store.c`：按主题保存最新的视图模型，带版本号，变化时发事件；
  - `svc/store.c`：SPEC §6.15 的 NVS 命名空间读写；
  - `svc/log.c`：日志输出框架（CDC 与环形日志的后端在 FW-15、FW-26 中接上）；
  - 任务看门狗配置与重启原因记录。
- **验收**：
  - `idf.py build` 通过，CI 能编译；
  - 分区表与 SPEC 一致；
  - 上电后串口日志能看到启动的每一步，以及上次重启的原因；
  - 用一个测试主题写入 vm_store，订阅方能收到事件并读到最新版本。

### FW-01 I2C 总线与 AXP2101（M）
- **依赖**：FW-00
- **参考**：SPEC §4、H5–H9、H11、§6.5、§6.10.3
- **产出**：`board/i2c_bus.c`、`board/axp2101.c`
- **要点**：
  - 电源轨、TS 关闭、充电参数（300mA / 4.1V）；
  - 时序寄存器：reg0x27、reg0x22；
  - 读取开机原因；
  - `axp_power_off()`；
  - 中断标志的读取与清除。
- **验收**：
  - 串口日志能打印出电池电压、百分比、VBUS 和充电状态，与万用表的读数基本一致；
  - 调用 `axp_power_off()` 后，整机断电，按 PWR 能重新开机；
  - **为三个按键的物理位置拍照**，存放到 `docs/assets/keys.jpg`。

### FW-02 显示与 LVGL 接入（M）
- **依赖**：FW-01
- **参考**：SPEC H1–H4、H10、§6.3
- **产出**：`board/co5300_panel.c`、`gfx/gfx.c`
- **要点**：
  - 初始化表必须原样使用；
  - rounder；
  - draw buffer 放在内部 DMA RAM 并双缓冲；
  - 亮度伽马映射与 `gfx_fade_to`；
  - 面板睡眠与唤醒。
- **验收**：
  - 全屏纯色和渐变测试图正常，没有偏移、花屏或撕裂条纹；
  - 亮度可以平滑渐变；
  - 睡眠与唤醒循环 100 次，没有出现异常。

### FW-03 触摸（S）
- **依赖**：FW-02
- **参考**：SPEC §4.2
- **产出**：`board/cst9220_touch.c`，接入 LVGL 的触摸输入设备
- **验收**：
  - 四角和中心的点击坐标误差 ≤ 10px；
  - 熄屏后触摸中断能唤醒系统（配合 FW-09 验证）。

### FW-04 三键输入（M）
- **依赖**：FW-01
- **参考**：SPEC H6、H12、§6.9
- **产出**：`board/keys.c`、`svc/input.c`，以及语义事件 `KEYEV_*`
- **要点**：
  - 消抖、短按、长按（按住期间触发）、Key3 双击；
  - BOOT + Key3 组合键；
  - PWR 按住 2s 和 4s 两个阶段；
  - 熄屏时吞掉唤醒按键。
- **验收**：日志中能看到每一种按键事件，并且按附录 B 的"按键"一节逐项通过。

### FW-05 字体管线与资源包（M）
- **依赖**：FW-02、C-02
- **参考**：SPEC §6.4.2、§6.6.2
- **产出**：`tools/gen_fonts.py`、`tools/pack_assets.py`、`assets/nukapack.c`、`assets_src/`（字体放在这里，并附上 OFL 许可证）
- **要点**：
  - 中文常用字表加业务词表，字号 22 和 28，4bpp；
  - 资源包通过 mmap 映射；
  - 校验 ABI 版本；
  - 构建选项 `NUKA_LANG_PACK=en-only`。
- **验收**：
  - 表盘能用 112px 字号显示时间；
  - 中英文混排正常；
  - 资源包大小 ≤ 6MB。

## 8. 轨道 FE：ESP32 LVGL UI 优化（最后的大项任务）
> **范围**：只针对 ESP32 屏幕上的 LVGL UI，不涉及 Web。三个目标：
> 1. **功能完整度**：每个交互流程都走得通、没有死角；
> 2. **美观度**：精致的视觉与动效；
> 3. **低功耗**：在不损失流畅度的前提下，把亮屏、熄屏和待机的功耗压到最低。
>
> **可以改的**：
> - `*_view.c`；
> - `ui/` 中的视觉部分（`theme.c`、`anim.c`、`widgets/`）；
> - `assets_src/`；
> - `design/`（修改 token 的值要走契约流程）；
> - 功耗相关参数（§2.1）。
>
> **不改的**：`*_app.c`、`apps/app.h`、`ui/nav.c`、`ui/keynav.c`、svc 层的结构、协议。发现功能缺口时，写清楚交给 FW，或者在 PR 中与 FW 协调。
>
> **开工条件**：M6.5 系统联调通过。数据由 `nuka hub --demo` 提供，不需要真实的数据源。
>
> **验收方式**：以截图、录屏、性能 HUD 和电流测量为准，**不写测试**。

## 10. 风险
| 风险 | 影响 | 对策 |
|---|---|---|
| 没有 TE 同步，滑动时会撕裂 | 视觉效果 | 在 FW-07 和 FE-D3 实测；改用 B 方案作为备选 |
